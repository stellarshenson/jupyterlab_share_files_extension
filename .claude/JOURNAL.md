2. **Task [Extended] - Peer-to-peer file sharing implementation** (v0.6.13): Built complete AirDrop-style file sharing extension from scratch through seven phases plus extensive iteration on UX feedback<br>
   **Result**: Drove the extension from boilerplate to a working peer-to-peer file drop. Why this shape: shares are read-only file drops served from the creator's own Jupyter server (no shared filesystem assumed), requests are inboxes others can upload to, both produce 8-char base32 links that carry the entire credential. Backend uses `tornado.httpclient` to relay between peers when needed. `_PublicBase` extends `tornado.web.RequestHandler` (NOT `JupyterHandler`) - the latter's `prepare()` enforces identity checks that 500ed unauthenticated requests behind JupyterHub even with `check_xsrf_cookie` overridden. Frontend is a vanilla-DOM Lumino `Widget` (same pattern as `claude_code_extension`) - no React. Storage layout `<workspace>/uploads/{shares,requests}/<slug>-<id>/` - slug-prefix makes folders human-findable, `_path_for` scans for `-<id>` suffix with backward-compat for legacy plain-id folders. `ShareStore.list()` re-scans `data/` directories on every call because the manifest.json's cached `entries` array goes stale after `add_items` - this was a bug where dropped files briefly highlighted but never appeared in panel. Path safety: `_is_safe_relative` blocks `..` and absolute paths syntactically but does NOT call `.resolve()`, so symlinked workspace entries like `@shared/...` work transparently (earlier resolve-and-check rejected them). Self-connect blocked both frontend (`window.location.host` compare) and backend (404). Settings schema at `schema/plugin.json` exposes `enableShares` and `enableRequests` toggles wired via `ISettingRegistry.load` + `settings.changed.connect`, live-updating the panel without reload. Build needed `license-webpack-plugin` patched in postinstall - the v2.3.21 (and v4.0.2) ships `filename.split('=')[1].trim()` which throws on webpack 5's `provide module` identifiers that have no `=`. Patched via `scripts/patch-license-webpack-plugin.js` run from npm `postinstall` hook. UX iterations driven by live testing: copy-link icon flashes + opens popup with selectable link (no toast - popup IS the feedback), section headers became named dividers using CSS `::before`/`::after` flex separators (no expand-triangle), Save All removed entirely (files just live where they live, path shown via `GET /api/info` rendered in italic footer line), entry fonts dropped to `--jp-ui-font-size0` to match file-browser density, default storage moved from `.jupyterlab_shares` to plain `uploads` (visible, non-dot prefix). README rewritten to describe the actual feature set, storage layout, and `c.ShareFilesConfig.shares_dir` config knob. Verified end-to-end with curl against a real Jupyter server and live JupyterHub at `jupyterhub.lab.stellars-tech.eu`.

4. **Task - Fix [x] remove button via DELETE-without-body** (v0.6.15): Per-file remove button silently failed because the DELETE body was being stripped between browser and Tornado<br>
   **Result**: Clicking [x] on a share entry or request upload did nothing - backend always returned 400 ("names must be non-empty list"). Root cause: browser `fetch()` includes the JSON body on DELETE but JupyterLab's `ServerConnection.makeRequest` and intermediate proxies (Traefik, JupyterHub) routinely strip DELETE bodies. Fix: switched both endpoints to query parameters - `DELETE /api/shares/<id>/items?name=foo&name=bar` (Tornado `self.get_arguments("name")` accepts repeated keys) and `DELETE /api/requests/<id>/uploads?uploader=...&name=...`. Frontend wrappers in `src/api.ts` build the query string with `encodeURIComponent`. Removed the now-unused `jsonDeleteBody` helper.
